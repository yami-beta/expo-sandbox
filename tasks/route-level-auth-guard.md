# ページ単位で自由に認証必須を設定できる仕組み(フォローアップ)

## 背景

`feat/auth-sample` ブランチで Expo Router 公式 Protected Routes パターン
(https://docs.expo.dev/router/advanced/authentication/) のサンプルを実装した際、
「`/auth` 配下だけでなく、アプリ全体の各ページごとに認証必須か否かを自由に設定
できるようにしたい」という要望が挙がった。

これは「ログイン処理のサンプル」という1機能に閉じたスコープを超え、認証が
アプリ全体の関心事になる大きな設計変更のため、今回の PR には含めず別作業とする
ことで合意した(2026-07-16)。

## やりたいこと

任意のページ(ルート)ごとに「認証済みでないとアクセスできない」を宣言的に
設定できるようにする。既存の20以上のサンプル画面のうち、どれを認証必須にし、
どれを公開のままにするかを自由に選べる状態を目指す。

## 判明している技術的制約(要考慮)

`Stack.Protected` でガードが外れた画面へのフォールバックは、
`unstable_settings.anchor`(旧 initialRouteName)に静的に戻る仕様で、
ランタイムのガード状態を考慮しない(expo-router の `getRoutesCore.js` /
`StackRouter.js` の実装、GitHub issue expo/expo#37305 で同じ症状が多数報告
されている既知の制約)。

つまり「対象ページを個別に `Stack.Protected` で包む」という素朴な実装では、
そのページが `(home)` Stack のような「anchor設定＋多数の兄弟画面を持つ既存Stack」
に属している場合、未認証でアクセスすると sign-in ではなく anchor 側(ホーム一覧)
に落ちてしまう不具合が、対象ページごとに再発する可能性が高い。

`feat/auth-sample` では、この問題を「認証対象の2画面(index/sign-in)だけを
anchor無しの独立したネストStackに分離する」ことで解決した
(`apps/sandbox/src/app/(tabs)/(home)/auth/_layout.tsx` 参照)。ページ単位で
自由に設定できる仕組みにする場合、恐らく個々のサブStackにガードを散りばめる
方式ではなく、ルートレベルでの一元的なゲート機構が必要になる。

## 検討すべき論点

- **デフォルトの姿勢**: 公開をデフォルトにしてオプトインで保護するか、
  保護をデフォルトにしてオプトアウトで公開にするか
- **未認証時の挙動**: 保護されたページに未認証でアクセスした場合、
  sign-in へリダイレクトするか、ホーム一覧へ戻すか(上記 #37305 の制約が関わる)
- **サンプル vs 実基盤**: 「パターンを示すサンプル」として実装するか、
  実際にこのアプリのナビゲーション全体で使う認証基盤として実装するか
- **ナビゲーション構造**: ルートレベル(`app/_layout.tsx` 直下)でのゲートが
  必要になる可能性が高く、その場合 `app/(tabs)/` 配下の既存ファイル群の
  再配置(例: `app/(auth)/(tabs)/...`)を伴う大きなリファクタリングになりうる

## 再利用できそうな既存実装

`feat/auth-sample` の `apps/sandbox/src/features/auth/`(`SessionContext.tsx`,
`useStorageState.ts`, `useSession.ts`)はセッション管理のロジックとして
そのまま再利用できる見込み。設計し直しが必要なのは主にルーティング構造側。
